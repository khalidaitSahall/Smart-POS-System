# تخطيط النظام وتصميم هيكل الملفات وقاعدة البيانات

## 1. هدف النظام

تطبيق نقاط بيع وإدارة مخزون للمحلات التجارية، يعمل محلياً دون اتصال بالإنترنت (Offline-First)، مع قابلية إضافة مزامنة بين الأجهزة لاحقاً. يغطي البيع والفواتير والمنتجات والمخزون والعملاء والموردين والمشتريات ودرج النقدية والتقارير.

## 2. البنية المقترحة

- **واجهة المستخدم:** React وTailwind CSS.
- **تطبيق سطح المكتب:** Electron؛ يتواصل مع الواجهة عبر واجهات آمنة يوفّرها `preload.js`.
- **الخادم المحلي:** Node.js وExpress، ويقدّم API للواجهة.
- **قاعدة البيانات المحلية:** SQLite، مع تفعيل المفاتيح الأجنبية والمعاملات.
- **المزامنة المستقبلية:** طبقة مزامنة مستقلة؛ لا تعتمد الواجهة مباشرة على قاعدة البيانات أو مزود المزامنة.

### تدفق الطلب

`React UI → API client → Express routes → middleware → controllers → services → repositories → SQLite`

- **Routes:** تعريف المسارات والتحقق الأولي من المدخلات.
- **Controllers:** تحويل طلبات HTTP إلى استدعاءات خدمات وإرجاع الاستجابات.
- **Services:** قواعد العمل والمعاملات، مثل إتمام البيع وتحديث المخزون.
- **Repositories:** الاستعلام عن قاعدة البيانات دون خلط SQL بمنطق الواجهة.
- **Middlewares:** المصادقة والصلاحيات والتحقق من الطلبات ومعالجة الأخطاء.

## 4. قواعد التصميم

1. تتم عملية البيع وتسجيل بنودها وتخفيض المخزون وتسجيل حركة المخزون في **معاملة واحدة**؛ إما أن تنجح كلها أو يتم التراجع عنها.
2. تحفظ الأسعار والمبالغ بوحدات العملة الصغرى كأعداد صحيحة لتجنب أخطاء الكسور العشرية.
3. لا تحذف الفواتير المسجلة حذفاً نهائياً؛ تُستخدم حالة الإلغاء أو الاسترجاع مع حفظ الأثر المحاسبي.
4. تحفظ كلمات المرور باستخدام تجزئة آمنة، ولا تحفظ كنص صريح.
5. يجب تسجيل المستخدم والوقت في العمليات الحساسة، مثل البيع والتعديل على المخزون.
6. تبقى طبقة المزامنة اختيارية ولا تمنع التشغيل المحلي عند انقطاع الشبكة.

## 5. الكيانات والعلاقات الأساسية

- التصنيف `categories` يضم منتجات متعددة `products`.
- المنتج يرتبط بحركات مخزون `stock_movements` وبنود البيع `sale_items` وبنود الشراء `purchase_items`.
- الفاتورة `sales` تتبع مستخدماً، ويمكن أن ترتبط بعميل، وتضم بنوداً متعددة.
- الشراء `purchases` يتبع مورداً ويضم بنوداً متعددة.
- جلسة درج النقدية `cash_registers` تتبع مستخدماً، وتجمع عمليات البيع والمدفوعات النقدية خلال الوردية.
- العميل والمورد اختياريان في مواضع البيع/الشراء التي تسمح بذلك.

## 6. مراحل التنفيذ المقترحة

1. اعتماد هذا التصميم وإنشاء migrations وبيانات تجريبية.
2. تنفيذ إعداد قاعدة البيانات والمصادقة والصلاحيات.
3. تنفيذ المنتجات والتصنيفات وحركات المخزون.
4. تنفيذ البيع والفواتير والطباعة ضمن معاملات ذرية.
5. تنفيذ العملاء والموردين والمشتريات والديون ودرج النقدية.
6. تنفيذ التقارير والنسخ الاحتياطي والاختبارات.
7. إضافة المزامنة متعددة الأجهزة بعد استقرار الاستخدام المحلي.

> مخطط SQL الأولي موجود في `database-schema.sql`. ينبغي تحويله إلى migrations قابلة للتحديث قبل نشر التطبيق للمستخدمين.
